Marco conceptual

Qué es TDD

TDD no consiste en escribir tests, sino en escribir el test antes que el código y dejar que ese test condicione el diseño. El test deja de ser una tarea posterior y pasa a funcionar como la especificación ejecutable del requerimiento.

1RED

Se escribe un test que falla, porque el código que necesita todavía no existe. Un test que nunca falló no prueba nada: no hay evidencia de que esté verificando algo.

2GREEN

Se escribe el mínimo código que hace pasar ese test. No el código definitivo ni el más elegante: el mínimo.

3REFACTOR

Con el test en verde como red de seguridad, se mejora el código. Si el cambio rompe algo, el test lo reporta de inmediato.

El ciclo aplicado, con corridas reales

Las dos terminales corresponden al CRUD de Go. Muestran el mismo test en los dos estados: primero fallando porque el constructor todavía no rechaza el título vacío, y después pasando una vez agregada esa validación.

RED el test falla: el código aún no existe

Falla únicamente la fila titulo_vacio del caso de prueba; las otras cuatro pasan. Esa granularidad es la que aportan los subtests: la falla señala el caso exacto.

GREEN el mínimo código que lo hace pasar

Se incorpora la validación del título al constructor. Nada más: cualquier mejora posterior corresponde al paso de refactor, ya con el test cubriendo el comportamiento.

crud-tdd/go/pelicula.go — las cuatro líneas que van de RED a GREEN
  if titulo == "" {
      return Pelicula{}, fmt.Errorf("%w: el titulo no puede ser vacio", ErrDatosInvalidos)
  }

Testing unitario: unitario frente a integración

  

    El ejercicio resuelve una ecuación de primer grado del tipo ax + b = c, despejando
    x = (c - b) / a. El código se dividió en dos clases con responsabilidades separadas:
  

  
    
    
  • Parseador — interpreta el texto: separa "2x - 1 = 0" en
      a = 2, b = -1, c = 0.
    • 
    
  • EcuacionPrimerGrado — aplica la fórmula del despeje. Depende del
      Parseador, y rechaza a = 0 porque dejaría de ser de primer grado.
    • 
  

  

    Esa división es la que permite ilustrar el punto central del artículo: la diferencia entre un test
    unitario y uno de integración. Por eso el ejercicio tiene tres archivos de test y no uno.

Por qué se usa un mock

  

    EcuacionPrimerGrado depende de Parseador. Si la fórmula se prueba con el
    parseador real y el test falla, no queda claro cuál de las dos clases tiene el defecto. Mockito
    resuelve eso reemplazando la dependencia por un doble de prueba programado.
  


  

    

      
Test unitario aislado — con mock

      

        
EcuacionPrimerGradoMockitoTest.java

        

      

      

        Este test no parsea nada. Le indica al doble qué devolver y verifica una sola cosa: que
        con a=2, b=-1, c=0 la fórmula dé 0.5. Si el parseador real se rompe,
        este test sigue pasando y el que falla es ParseadorTest, que es donde está el
        defecto. Eso es aislar la unidad.
      

    

    

      
Test de integración — sin mock

      

        
EcuacionPrimerGradoIntegrationTest.java

        

      

      

        El mock tiene un punto ciego: asume que el parseador devuelve lo que el test declaró. El test
        de integración ejecuta la cadena completa con el parseador real, y es el único que verifica
        que las dos clases encajan. Ambos tipos son necesarios.

El modelo funcional común

  

    Los seis proyectos resuelven el mismo problema con distinto dominio. Fijar el problema hace que lo
    único que varíe entre proyectos sea el lenguaje.
  

  

    
1Entidad validada

      
Campos obligatorios y un rango de año admitido. Las reglas viven en un solo lugar.

    
2Repositorio en memoria

      
Alta, consulta por id, listado, modificación parcial y baja.

    
3Identificadores internos

      
Autoincrementales, asignados por el repositorio y no por quien lo invoca.

    
4Dos clases de error

      
Datos inválidos y entidad inexistente, siempre distinguibles desde el test.

  

  

    Los nombres de los casos de prueba siguen el mismo patrón en los seis
    (deberia_<comportamiento>_<condición>), de modo que se pueden comparar
    caso por caso entre lenguajes.

Las tres formas de probar un error

  

    El mismo caso de prueba en los seis proyectos —consultar un identificador que no existe— se
    escribe de tres maneras distintas según cómo el lenguaje represente el fallo.
  

  

    

      
1 · Excepciones
C#, Python, PHP, React

      
with pytest.raises(ViniloNoEncontradoError):
    repositorio.obtener_por_id(999)

      
El fallo viaja por un canal separado del valor de retorno, así que el test
        necesita un mecanismo específico para capturarlo.

    

    

      
2 · Valor de retorno, verificado por el compilador
Rust

      
let resultado = repositorio.obtener_por_id(999);
assert_eq!(resultado, Err(ErrorCatalogo::VideojuegoNoEncontrado(999)));

      
El error es el propio resultado, y se compara con la misma aserción de igualdad
        que el caso correcto. El compilador no permite ignorarlo.

    

    

      
3 · Valor de retorno, verificado por convención
Go

      
_, err := repositorio.ObtenerPorID(999)

if !errors.Is(err, catalogo.ErrNoEncontrada) {
    t.Errorf("se esperaba ErrNoEncontrada, se obtuvo: %v", err)
}

      
También es un valor, pero repositorio.Eliminar(id) sin asignación
        compila igual. Acá el test es la única verificación de que el error se propaga.

Conclusiones

  
    
    
  1. 
      Escribir el test primero condiciona el diseño, no solo la confianza. Los seis
      repositorios terminaron asignando los identificadores internamente y no dejándolos en manos de
      quien los invoca, porque el primer test escrito fue el del identificador autoincremental. La
      decisión de diseño la forzó el test.
    
    2. 
    
  2. 
      Usar un mock no es evitar la prueba: es decidir qué se está probando. El test con doble
      y el de integración responden preguntas distintas y ninguno reemplaza al otro. El primero
      localiza el defecto; el segundo verifica que las piezas encajen.
    
    3. 
    
  3. 
      El ciclo es idéntico en los seis lenguajes; lo que cambia es qué puede expresar el test.
      El caso más claro es el tratamiento del error: con excepciones, con un Result que
      el compilador obliga a atender, o con un valor de error que nadie obliga a mirar. Cuanto menos
      cubre el lenguaje, más responsabilidad recae sobre el test.
